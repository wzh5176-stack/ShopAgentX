# 官方沙箱付款入口：本机验收

2026-10-24，用户手写完成后独立验收。正式 207 个 Java 源文件用 Java 17 / Maven 编译打包成功（`-DskipTests package`，不是 JUnit 全套测试）。本次正式构建的受控 HTTP、真实 MySQL 与事务检查 **96/96 通过**。

证据：[结构化结果](verification/alipay-checkout-formal-2026-10-24.json)。此结论仅覆盖付款入口，尚不是完整支付宝付款闭环。

## 已验证的行为

- Windows MySQL 8.0.34 的 shopagent 库实际已有 027 的五列、渠道/身份/成功证据检查与两个新唯一索引；保留原有活动支付/成功支付生成列约束。本次没有执行 DDL 或授权。
- 正式打包 JAR 的 `POST /api/payments/alipay/page`：本人 USER + CSRF，200，`Cache-Control: no-store`，返回 `data.payment / outTradeNo / payUrl`。匿名 401、仅 ADMIN 403、CSRF 403、他人/不存在订单 404、参数 400。
- 金额和到期时间取订单；忽略客户端试图覆盖金额、渠道、状态等字段。交易号、应用及商家身份持久化。重复同键返回原支付与交易号；新键遇活动支付 409；并发同键复用、不同键只有一张活动支付。配置商家身份变化时拒绝复用原请求。
- 采用临时生成的测试 RSA 密钥、虚构数字 APPID/PID，调用正式配置与 SDK 本地生成链接；校验沙箱 HTTPS、请求 RSA2 签名、金额、商户交易号、产品码、标题和截止时间。未读取用户私钥或其私密配置，未打开签名链接、提交交易或调用官方 API。测试材料不能作为用户真实沙箱账号可用的证明。
- 付款准备不再次预占库存。真实 INSERT 后注入异常、保存后读回失败均回滚；签名时没有数据库事务，支付已提交且其他连接可见；即使外围事务回滚/签名失败，已提交支付保留，同键可重新生成链接。
- 官方 PENDING 结果未知时，本地取消和过期受保护，不释放库存。旧 MOCK refresh 返回 409；MOCK 结果入口对官方单返回 404 PAYMENT_NOT_FOUND；MOCK 补偿扫描跳过官方单。
- 定向 MOCK 回归：创建、付款成功消费预占/订单 PAID、重复刷新幂等、取消关支付并释放库存均通过。本次没有重新运行上个版本全部 369 项检查。
- 实测 SDK 初始化后 JVM 证书算法禁用策略恢复为初始化前值。

## 数据与运行边界

两个临时审计 Java 进程仅在本机随机端口运行，已停止。只在测试进程临时排除 Redis Session 自动配置，使用原生 Tomcat 会话；正式 Redis 配置未改。没有操作 Linux、VMware、模型、Git 或部署。

原有 12 张业务表的数据行摘要一致。审计新建账号、隐藏测试商品与终态订单/支付保留留痕；新建地址移除，测试待支付订单、PENDING 支付、库存预占均为 0。只有从未提交到支付宝的虚构 APPID/PID 测试支付被辅助 SQL 标记 CLOSED，然后用正式订单取消服务释放库存；这属于测试清理，不是官方关单功能验收。

最初辅助脚本把付款请求当通知验签，且未识别 MySQL CHECK 错误 3819 的 JDBC 异常映射；预检中断后已清理。第二轮辅助脚本把既有 MOCK 渠道隔离的预期 404 写成 409。两份报告保留为 `alipay-checkout-preflight-2026-10-24.json` 与 `alipay-checkout-r1-2026-10-24.json`，不计入最终通过项；修正仅涉及临时审计脚本，没有改用户正式 Java/SQL。本次最终 96 项使用同一正式源/JAR，指纹未变。

SDK 请求签名与通知验签内容的区别参见[官方 AlipaySignature 源码](https://github.com/alipay/alipay-sdk-java-all/blob/master/v2/src/main/java/com/alipay/api/internal/util/AlipaySignature.java)。审计请求链接使用保留 sign_type 的待验签内容；后续通知入口须另按通知协议实现，不能照搬审计请求验签。
