## 并发和旧快照

受控供应商响应在模型调用位置暂时阻塞，确保请求捕获同一个旧会话版本，再同时释放，不靠顺序请求假装并发。

1. 两个明确工具请求：一200、一409 CONVERSATION_CHANGED；仅赢家保存一操作和一对消息。
2. 两个澄清请求：一200、一409；仅保存赢家一对TEXT消息，没有操作单。
3. 工具等待模型时，旧普通导购能成功提交；放行旧工具结果后返回409，没有孤立操作或消息。这也证明没有在等模型时一直持有会话写锁。
4. 工具与旧普通导购竞争：只有一个保存成功，消息/操作数量与赢家类型一致。
5. 工具与旧流式导购竞争：只有一个提交成功；流式失败按SSE错误返回（其HTTP可为200），不把网络200误记成业务成功。
6. 实际MySQL RR事务先建立旧消息快照，外部正式HTTP提交新澄清消息后，原工具写入服务通过锁内当前读仍识别版本冲突。该旧快照探针外层回滚，最终仅保留真实HTTP提交的消息。

本轮未以并发测试估算吞吐或生产容量，模型供应商响应受控，不是实际DeepSeek语义准确率证明。
