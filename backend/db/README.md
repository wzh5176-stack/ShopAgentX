# 数据库结构与迁移约定

本目录管理可审查的结构基线和历史文件指纹。它不会在应用启动时自动迁移数据库，也不代表现有 Windows/Linux 数据库已执行过清单里的每一步。

## 三类材料的职责

| 材料 | 用途 | 执行范围 |
| --- | --- | --- |
| `../sql/001_...027_...sql` | 原始教学与历史迁移，含建库、数据、账号、授权、核对语句 | 按历史场景人工选择；禁止整目录重放 |
| `migration-manifest.json` | 逐文件分类、编号及按 LF 归一化的 SHA256 | 只读源文件校验，不是数据库已执行台账 |
| `schema-baseline.sql` | 从已审查历史提取的 13 表结构及 ALTER，排除建库、USE、种子与授权 | 仅全新空库；回归测试会主动检查空库 |

离线校验：在仓库根目录运行 `python scripts/check_migrations.py`。

## 已有数据库升级

1. 确认数据库地址、库名、MySQL 版本与执行账号。Windows `127.0.0.1` 账号与容器 `%` 账号不能混用授权脚本。
2. 导出备份，在独立实例恢复并核对。保留备份文件名、校验和、表结构与行数证据。
3. 对比目标库的表、列、索引和约束，确定缺少的变更；不能只根据文件编号推断。
4. 新增独立的增量迁移，写清前置条件、影响、验证 SQL、恢复方案和必要权限。
5. 先在隔离恢复库执行并跑回归，再按部署步骤操作目标环境。
6. 记录目标环境、执行时间、文件校验和与结果。失败先检查实际结构，禁止盲目重跑。

MySQL DDL 不应被当作普通业务事务可全部回滚。恢复有数据的数据库时，需要先确认新版本写入的数据如何处理，不能仅靠回退应用镜像。

## 新迁移的维护

- 已归档的 001–027 历史不再就地修改。追加编号文件；同时更新分类清单、审查其校验和。
- 架构变更与演示数据、账号、授权分开。不要在应用运行账号下执行 DDL。
- 更新空库基线时同步审查清单；校验器会检查它与所有 `schema` 类历史中的 CREATE/ALTER 完全一致。
- 修改清单不能作为绕过失败的操作：先确认改动有意、迁移前置条件完整，再评审更新。
- 未来引入 Flyway/Liquibase 时需要单独设计现有库的接管和数据库端版本台账；本次没有启用自动 baseline 或自动迁移。

## 新空库与回归库

回归专用库名为 `shopagent_regression`。集成测试只接受 loopback 地址、显式开关以及零表空库；拒绝已有表的库，不执行 DROP DATABASE 或 TRUNCATE。

`schema-baseline.sql` 不含演示商品、库存初始化行、真实账户或密码。测试自行创建虚构数据。

该基线可用于审查新环境的结构初始化，但不是现有 ShopAgent 环境的升级脚本。历史 019 中的库存种子不会混入基线，不会把库存重置为 20。

详见 [自动化回归说明](../../docs/REGRESSION.md)。

2026-10-25追加028补货审计表与029本机授权，001–027保持不变；空库基线为13表17条结构语句。现有库只增量执行028和对应账号授权，详docs/INVENTORY_CLOSURE.md。
